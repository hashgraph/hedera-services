# Pre-sizing and bounded chains — October 13, 2026

[Latest summary](results.md) · [All measurements and calculated comparisons](f1-f2-20261013.json)

This report covers the separate-fix experiments. The [October 14 follow-up](f1-f2-combined-20261014.md)
tests F1 and F2 together; the measurements below remain unchanged.

## What changed

This run tested two possible ways to reduce the shared pools' snapshot-time regression:

- **F1, pre-sizing:** use `RandomAccessFile.setLength()` to set the output index's logical length
  before chunk writes. This does not reserve all physical storage in advance.
- **F2, bounded chains:** split each index into up to eight contiguous ranges. Submit one chunk
  from each range, then submit its successor when it finishes. Unlike the baseline, this still
  schedules a task for every chunk; a chain need not stay on one worker.

The range baseline used P=8 writers per index. The task and fixed-pool implementations used
B=24 shared workers; F2 used K=8 chains per index. This roughly aligns writer budgets, not actual
concurrency. The shared pools also run hash flushing, metadata and hard-link operations.

There were eight variants: baseline control/F1, tasks control/F1/F2, and fixed pool control/F1/F2.
Each control used the same experiment JAR as its modified variants, with both flags disabled.
F1 and F2 were not combined. Only this selected budget was tested, not the production defaults
or the full parallelism sweep.

## What the results support

Pre-sizing matters for snapshot return time, including in the baseline. This supports treating
file growth as a useful optimization target, but does not prove which filesystem operation or
lock caused the original slowdown.

Bounded chains also help. F2 changes per-index concurrency, queue depth and write order together,
so the result cannot identify which of those caused the improvement. It does not establish that
contiguous writes alone explain the baseline's advantage.

Once both sides get F1, tasks are 4.9% faster than the baseline for DISK_SEGMENT, approximately
tied for DISK, and 3.8–14.5% slower for the other three implementations. The fixed pool remains
2.3–17.8% slower on mean time. Thus beating the unchanged baseline is not enough to justify
switching scheduling models.

F1 + F2 was not measured in this run. Their improvements must not be added together; see the
[combined follow-up](f1-f2-combined-20261014.md) for that measurement. This run did not select
a production winner or establish a reason to change the default parallelism.

## Repeatability and limits

The run rotated implementation and variant order across three interleaved blocks. Each
configuration had one fresh JVM per block, one warmup and three measured snapshots. These are
three independent fork blocks, not nine independent forks. Block comparisons are descriptive;
the runs were not simultaneous, and no formal significance claim is made.

- Tasks + F1 versus baseline + F1 on DISK: -1.0%, -1.9%, +2.3% by block. The -0.2% overall
  difference is a tie, not a reliable win.
- The same comparison on DISK_SEGMENT: -7.0%, -1.5%, -6.1%. Its direction repeats in all blocks.
- Tasks + F2 on OFF_HEAP is -0.3% versus the unchanged baseline by mean, but +0.1% by median.
  Fixed-pool + F2 on SEGMENT is -0.2% by mean, but +0.3% by median. Treat these as close results.
- No sample was removed, including the 9.414-second task-control DISK_SEGMENT sample in block B.
  Raw samples, medians and block means are preserved in the JSON.

The new controls reproduce the earlier pool regression. They are not byte-identical to the
October 7/8 JARs: this campaign rebuilt historical source with experiment switches and tests.
The same-run controls are therefore the primary reference. As context, the new OFF_HEAP
baseline mean was 7.3% higher than on October 7; other control changes were smaller. This is
another reason not to mix days when calculating F1/F2 benefits.

## Workload and timing

- Same saved one-billion-record fixture, about 258 GiB; 32-byte keys and 128-byte values.
  It was generated on October 5 and was not rebuilt here.
- Chunk size: 1,048,576 longs. Hash chunk height: 6; 262,144 cached hash chunks loaded per trial.
- Linux NVMe/ext4 host, AMD EPYC 9124, 16 cores/32 logical CPUs, about 125.5 GiB RAM.
  Temurin 25.0.2+10, JMH 1.37, `-Xms4g -Xmx32g -XX:MaxDirectMemorySize=16g`.
- Only the snapshot call is timed. Source preparation, cache loading, file forcing, validation
  and cleanup are outside it. Hash-cache flush overlap is enabled; final index-file forcing is
  disabled inside the call. Snapshot return time remains the decision metric.
- 40 configurations, 120 forks, 360 measured snapshots and 120 warmups. All completed.
- Whole run: 2h 35m 56s. The measurement session, including per-fork setup/teardown, took
  2h 34m 06s. Builds ran before measurement; no fixture generation was needed.

## Validation and machine activity

All 1,391 top-level archived-file checksums pass. Including nested manifests, 125 checksum lists
contain 2,558 successful checks. Archived patches and runner match the committed experiment
files. All three builds succeeded; their 163 focused tests passed (baseline 7, tasks 128,
fixed pool 28).

All 120 source preparations and 480 snapshot validation paths completed, including warmups.
The benchmark checks index lengths/headers and sampled values, metadata and store presence;
it does not restore and compare every record. There were no benchmark failures or application
errors. Fixture inventories before and after match all 357 entries: names, sizes and modification
times, not full-content hashes.

Resource sampling covered every cell, normally every five seconds, with no gap above six seconds.
The first historical `top`/`vmstat` reports were excluded from interval summaries.

| Observation | Result |
|---|---|
| Process/CPU, memory/swap, disk samples | 1,842 / 1,850 / 1,837 |
| Minimum available RAM | 111.3 GiB |
| Swap activity | No swap-out; one small 7 KiB/s swap-in interval |
| Largest other userspace CPU sample | `cf-agent`, 74.9% of one core (2.3% of the machine) |
| Java processes | At most two at once, consistent with launcher plus benchmark fork |

There is no evidence of sustained memory pressure or another large userspace workload. However,
the host was not completely idle: system-management processes ran periodically. A resource-only
screen, selected without looking at snapshot scores, found 20 possible measured-snapshot overlaps
across 17 fork cells. It flags process CPU of at least 2% of one core; that is a screening threshold,
not proof of an effect on performance. Thirteen overlaps also contain a process sample timestamp
inside the logged snapshot interval. Five-second samples cannot pinpoint the exact overlap or
attribute every disk operation to a process.

For example, block C's third baseline-F1 HEAP snapshot ran from 18:26:58.813 to 18:27:04.082 UTC.
At 18:27:03, `cf-agent` used 50.7% of one core; package-management processes were also visible in
that period. These are real concurrent activities, not benchmark writer threads.

No measurements were removed. As a secondary check, every F1/F2-versus-own-control comparison
still has at least one block with no flagged measured overlap on either side, and the improvement
persists in all such blocks. This supports the broad improvement, not a claim that tiny differences
are reliable or that the machine was perfectly isolated. Exact intervals and archive-relative log
references are in the JSON's `resourceSummary`.
